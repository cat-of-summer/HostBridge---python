# HostBridge

Локальный DNS-резолвер и управление виртуальными доменами разработки для Windows и Linux.

Заменяет ручную правку системного `hosts` при работе с сайтами, привязанными конфигурацией
к конкретным доменам: домен заводится в интерфейсе или подхватывается из Docker и Traefik,
включается и выключается на лету, и результат виден в браузере сразу.

> [!warning]
> Проект в разработке. Готовы этапы **M0–M10**: резолвер, перехват имён, консоль, окно,
> Docker, Traefik, служба, Linux, настройки и оформление. Осталось выпустить релиз.

## Как это работает

Общесистемный DNS **не подменяется**. Вместо этого приложение поднимает DNS-сервер на
`127.0.0.1:53` и регистрирует правила только для своих пространств имён:

- **Windows** — NRPT (Name Resolution Policy Table), штатная таблица «пространство имён →
  резолвер». Она живёт в DNS Client выше настроек адаптеров, поэтому не зависит от VPN- и
  TUN-адаптеров, а `127.0.0.1` не попадает в таблицу маршрутизации и не перехватывается
  туннелем.
- **Linux** — маршрутизирующие домены systemd-resolved на **отдельном интерфейсе**
  (`hostbridge0`, dummy, адрес `169.254.53.1/32`). Настоящие сетевые интерфейсы не трогаем
  вовсе: `resolvectl dns eth0 …` заменяет серверы, выданные DHCP, а одни только
  маршрутизирующие домены снимают у линка признак `DefaultRoute` — вместе это ломает
  разрешение всех остальных имён. Свой линк даёт ровно ту же аддитивность, что и NRPT.

Из этого следует главное свойство: падение HostBridge ломает только его собственные домены,
но не разрешение имён вообще. Бонусом появляются wildcard-домены (`*.dobroedelo.ru`),
которых через `hosts` не добиться в принципе.

Маршрутизацию на порты и терминацию TLS приложение на себя не берёт — это остаётся за
Traefik или другим обратным прокси.

## Откуда берутся домены

Три источника, и они не мешают друг другу: проход синхронизации трогает только свои записи,
а созданное вручную не перезаписывается никогда.

**Вручную** — окно, интерактивная консоль (`hostbridge-cli`) или `domains.json`.

**Traefik** — `GET /api/http/routers`, из правил берутся аргументы ``Host(`…`)`` и
``HostSNI(`…`)``. Опрос раз в 10 секунд. Включается тем, что в настройках задан адрес API;
пустое поле — значит не импортировать. Недоступный Traefik — это *не* пустой Traefik:
записи остаются на месте, а не удаляются до следующего удачного опроса.

**Docker** — метки контейнеров, полный скан плюс поток событий (`start`, `die`, `destroy`),
переподключение с нарастающей паузой и полная пересинхронизация на каждом переподключении.
Читаются две схемы меток. Своя:

```yaml
labels:
  hostbridge.enable: "true"                  # обязательно: без него метки не читаются
  hostbridge.domain: "shop.test"
  hostbridge.domains: "api.shop.test,*.cdn.shop.test"
  hostbridge.address: "127.0.0.1"            # необязательно
```

и Traefik'овская — `traefik.http.routers.<имя>.rule` разбирается тем же парсером, что и API.
Контейнер, у которого уже есть правило с ``Host(`…`)``, ничего дописывать не должен:
объявленное правило и есть согласие. Для собственных меток `hostbridge.enable` обязателен —
иначе список заполнился бы всем, что запущено на машине.

Имя принадлежит имени, а не контейнеру: если один и тот же хост объявляют два контейнера
(сервис и его редирект), запись остаётся одна и не исчезает при остановке одного из них.

Метки читаются всегда — отключить импорт из Docker нечем, и незачем: на машине без движка
цикл просто не находит, с кем говорить, и уходит в паузу.

> [!note]
> Домен, пришедший из меток или из Traefik, в окне **не правится и не удаляется** —
> управление им делегировано контейнеру или роутеру, и правка была бы отменена следующим
> проходом синхронизации, а удаление отменилось бы им же. Меняют такой домен там, где он
> объявлен: в `compose.yml` или в конфигурации Traefik. Выключить его галочкой «Вкл» можно —
> это намерение о разрешении имени, а не претензия на владение записью.

## VPN с защитой от DNS-утечек

Клиенты вроде sing-box (v2rayN, режим TUN, `strict_route`) ставят фильтр WFP:

```
layer:     FWPM_LAYER_ALE_AUTH_CONNECT_V4
condition: FWPM_CONDITION_IP_REMOTE_PORT == 53      ← единственное условие
action:    FWP_ACTION_BLOCK
```

Условия на адрес в нём нет, поэтому под блокировку попадает и `127.0.0.1`: сокет
привязывается, `netstat` его показывает, правило NRPT на месте — а запрос до резолвера не
доходит, и браузер говорит «не удалось найти IP-адрес». Ни одного видимого признака поломки.

Выше этого блока лежат два разрешения того же фильтра: по идентификатору приложения самого
VPN и **по индексу его интерфейса**. Второе и есть выход: локальный адрес туннеля
принадлежит этой машине, сокет на нём принимает пакеты обычным образом, а обращение к нему
фильтр разрешает своим же правилом.

HostBridge проверяет это при запуске: пробует достучаться до `127.0.0.1:53` и, если получает
отказ по правам (`WSAEACCES`), дополнительно слушает адрес, через который уходит исходящий
трафик, и добавляет его в правило NRPT вторым сервером. Loopback остаётся первым, поэтому
пара работает и с поднятым туннелем, и без него. Обходов и трюков здесь нет — используется
разрешение, которое VPN написал сам.

Выключается настройкой `bypass_dns_filter: false`. Стоит выключить, если машина стоит в
сети, которой нельзя показывать резолвер: адрес выбирается по маршруту по умолчанию, и на
машине без VPN, но с каким-то другим фильтром порта 53, это может оказаться адрес в
локальной сети.

## Что происходит при запуске и закрытии

Резолвер поднимается сам. Окно открывается, и сразу за этим приходит запрос UAC: без
резолвера в программе нечего делать, и отдельная кнопка «включить» просила пользователя
подтвердить единственное, чего он мог хотеть. Отказались — окно работает дальше, а вверху
висит полоса с кнопкой, которой запрос можно повторить.

Само окно администратором не становится: манифеста повышения у него нет, повышается только
дочерний процесс демона. Поэтому окно по-прежнему читает профили браузеров текущего
пользователя и пишет в его домашний каталог.

Демон, запущенный из окна, получает его PID и следит за ним. Закрыли приложение — демон
это замечает и завершается штатным путём: снимает свои правила NRPT (или маршрутизирующие
домены resolved), сбрасывает кэш DNS и убирает `netstate.json`. Так же он поступает, если
окно не закрыли, а убили: следить за процессом надёжнее, чем полагаться на пункт меню.

Демон, установленный службой, PID владельца не получает — он принадлежит машине, переживает
закрытие окна и поднимается после перезагрузки. Если демон всё-таки убили жёстко, оставшиеся
правила снимает `hostbridge-cli --repair`.

## Linux

Проверено на Ubuntu 24.04 с systemd 255 и systemd-resolved, прогоном настоящего демона.

Резольвер заводит собственный интерфейс `hostbridge0` (dummy, `169.254.53.1/32`) и вешает на
него свой адрес и маршрутизирующие домены. Адрес обязателен: без него resolved показывает
`Current Scopes: none` и линк не используется вовсе. Настоящие интерфейсы не меняются —
`eth0` сохраняет серверы от DHCP и признак `DefaultRoute`, поэтому всё, что не наше,
резолвится как раньше. Остановка снимает интерфейс целиком, откат — `resolvectl revert`
плюс `ip link del`.

Служба (`--install-service`) кладёт юнит с `AmbientCapabilities=CAP_NET_BIND_SERVICE`. Это
проверено отдельно: под `nobody` без привилегии bind на порт 53 даёт `Permission denied`,
с ней — проходит, root не нужен.

Ярлыки — `hostbridge-cli --install-desktop`: пункт меню в
`~/.local/share/applications` и автозапуск сеанса в `~/.config/autostart`. Обе записи
пользовательские, права не запрашиваются. Убрать — `--uninstall-desktop`.

> [!warning]
> Если `/etc/resolv.conf` не указывает на `127.0.0.53`, программы идут мимо
> systemd-resolved через libc, и наши домены у них не разрешатся — при том что
> `resolvectl query` отвечает правильно. Демон это проверяет и пишет предупреждение в
> журнал. Лечится возвратом ссылки на `/run/systemd/resolve/stub-resolv.conf`.

## Настройки и Secure DNS

Во вкладке «Настройки» три поля: адрес API Traefik, интервал его опроса и язык интерфейса.
Всё остальное имеет ровно один правильный ответ для машины, на которой работает, а форма,
задающая вопрос с единственным правильным ответом, перекладывает работу программы на
пользователя. Адрес и порт прослушивания, upstream-резолверы, хост Docker и обход VPN живут
в `settings.json` как аварийные переключатели — там их и правят в тех редких случаях, когда
это нужно.

Хранятся эти три поля в разных местах, и это не случайно. Язык — предпочтение пользователя,
пишется прямо в `config.json` в его домашнем каталоге. Всё, чем пользуется резолвер, идёт
через control API: `settings.json` лежит в машинном каталоге, права на который принадлежат
тому, кто запускает демона (для службы — SYSTEM), и окно, работающее от пользователя, туда
писать не может. Редактируемые поля — список разрешённых, а не «всё подряд»: новое поле
нельзя будет отредактировать, пока кто-нибудь не решит, что можно.

Secure DNS не настройка, а диагноз, поэтому его в форме нет: профили браузеров читаются один
раз при запуске окна, и если хоть один ходит мимо системного резолвера — вверху появляется
полоса с предупреждением. Молчание значит, что всё в порядке. Читается это **в процессе
окна**, а не в демоне: демон повышен, и на Windows смотрел бы в профиль чужой учётной
записи. Ничего не меняется — только читается и показывается.

| Браузер | Настройка | Что означает |
|---|---|---|
| Chrome, Edge, Brave | `dns_over_https.mode = off` | всё в порядке |
| | `= automatic` | **тоже в порядке**: браузер переходит на DoH, только если системный резолвер — известный DoH-провайдер, а `127.0.0.1` таковым не является |
| | `= secure` | домены не откроются: все имена уходят на заданный endpoint |
| Firefox | `network.trr.mode = 0` или `5` | всё в порядке |
| | `= 2` | не в порядке, хотя называется «TRR first»: откат предусмотрен для сетевых сбоев, а NXDOMAIN на `shop.test` — совершенно успешный ответ |
| | `= 3` | не в порядке |

## Сборка из исходников

Нужен Python 3.10+.

```sh
bash build/build.sh          # Linux, macOS, Git Bash на Windows
pwsh build/build.ps1         # PowerShell
```

Результат — `dist/hostbridge-<os>-<arch>.tar.gz` на Linux и `.zip` на Windows.
`SKIP_TESTS=true` пропускает прогон тестов.

### Версия берётся из тега

Версия живёт в одном файле — `core/version.py`. `pyproject.toml` своего числа не хранит:
поле объявлено `dynamic` и читается из этого модуля, так что метаданные пакета и `--version`
бинарника разойтись не могут. В репозитории лежит `0.0.0` — честное описание сборки,
сделанной не из релизного тега.

Сборка по тегу `vX.Y.Z` вписывает версию в этот файл (`build/version_stamp.py`, вызывается из
обоих скриптов сборки). Тег — то, что видит пользователь и что он назовёт в баг-репорте,
поэтому выигрывает тег.

Откуда берётся число, по порядку:

1. аргумент — `python build/version_stamp.py v1.2.3`, для сборки руками;
2. `$HOSTBRIDGE_VERSION` — сюда CI кладёт `REF_NAME_NORM`, уже нормализованный ref
   (`1.2.3`, или `main-1.2.3` для тега с префиксом ветки);
3. `$GITHUB_REF_NAME` / `$GITHUB_REF` — сырой тег, если ничего не передали.

Команда сборки в CI (`BUILD_COMMAND`):

```sh
if [ "$RUNNER_OS" = Linux ]; then sudo apt-get update -qq && sudo apt-get install -y -qq libegl1 libgl1 libglib2.0-0 libxkbcommon0 libdbus-1-3 libfontconfig1 libgssapi-krb5-2; fi && if [ "$REF_TYPE" = tag ]; then export HOSTBRIDGE_VERSION="$REF_NAME_NORM"; fi && SKIP_TESTS=true bash build/build.sh
```

Проверка `REF_TYPE` обязательна: у ветки `REF_NAME_NORM` — это её собственное имя, и ветка,
названная `2`, без этой проверки стала бы версией `2`. Сырому тегу такая защита не нужна —
там версию опознаёт обязательная `v` впереди.

Ничего не коммитится — правится только рабочее дерево раннера. Сборка без тега (пуш в ветку,
pull request, локальный прогон) не трогает ни одного файла и остаётся на `0.0.0`.

Порядок здесь важен трижды: штамп ложится до `pip install -e .`, иначе метаданные возьмут
старое число; до того, как PyInstaller соберёт `core/version.py` в бинарник; и до
`CI_COMMAND` — в reusable-workflow шаг Build идёт раньше, поэтому `tests/unit/test_version.py`
проверяет уже проштампованное дерево.

## Разработка

```sh
pip install -e ".[dev]"
pytest -m "not docker and not admin" -q
ruff check .
```

Маркеры тестов: `docker` — нужен работающий демон Docker, `admin` — нужны права
администратора или root, `network` — тест открывает локальные сокеты.

Автотесты не запускают внешние процессы: `system.run` — единственный шов, через который
приложение вызывает `netsh`, `resolvectl` и подобное, и фикстура в `tests/conftest.py`
превращает такой вызов в падение теста. Иначе случайный `netsh`, сбежавший из юнит-теста,
переконфигурировал бы DNS тому, кто запустил `pytest`.
