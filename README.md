# HostBridge

Локальный DNS-резолвер и управление виртуальными доменами разработки для Windows и Linux.

Заменяет ручную правку системного `hosts` при работе с сайтами, привязанными конфигурацией
к конкретным доменам: домен заводится в интерфейсе или подхватывается из Docker и Traefik,
включается и выключается на лету, и результат виден в браузере сразу.

> [!warning]
> Проект в разработке. Готов этап **M0** — каркас, сборка и тесты. Резолвер, интеграции и
> графический интерфейс появляются на последующих этапах, см. «Состояние» ниже.

## Как это работает

Общесистемный DNS **не подменяется**. Вместо этого приложение поднимает DNS-сервер на
`127.0.0.1:53` и регистрирует правила только для своих пространств имён:

- **Windows** — NRPT (Name Resolution Policy Table), штатная таблица «пространство имён →
  резолвер». Она живёт в DNS Client выше настроек адаптеров, поэтому не зависит от VPN- и
  TUN-адаптеров, а `127.0.0.1` не попадает в таблицу маршрутизации и не перехватывается
  туннелем.
- **Linux** — маршрутизирующие домены systemd-resolved (`resolvectl domain <link> ~test`).

Из этого следует главное свойство: падение HostBridge ломает только его собственные домены,
но не разрешение имён вообще. Бонусом появляются wildcard-домены (`*.dobroedelo.ru`),
которых через `hosts` не добиться в принципе.

Маршрутизацию на порты и терминацию TLS приложение на себя не берёт — это остаётся за
Traefik или другим обратным прокси.

## Откуда берутся домены

Три источника, и они не мешают друг другу: проход синхронизации трогает только свои записи,
а созданное вручную не перезаписывается никогда.

**Вручную** — окно, интерактивная консоль (`hostbridge-cli`) или `domains.json`.

**Traefik** — `GET /api/http/routers`, из правил берутся аргументы ``Host(`…`)`` и
``HostSNI(`…`)``. Опрос раз в 10 секунд. Недоступный Traefik — это *не* пустой Traefik:
записи остаются на месте, а не удаляются до следующего удачного опроса.

**Docker** — метки контейнеров, полный скан плюс поток событий (`start`, `die`, `destroy`),
переподключение с нарастающей паузой и полная пересинхронизация на каждом переподключении.
Читаются две схемы меток. Своя:

```yaml
labels:
  hostbridge.enable: "true"                  # обязательно: без него метки не читаются
  hostbridge.domain: "shop.test"
  hostbridge.domains: "api.shop.test,*.cdn.shop.test"
  hostbridge.address: "127.0.0.1"            # необязательно
```

и Traefik'овская — `traefik.http.routers.<имя>.rule` разбирается тем же парсером, что и API.
Контейнер, у которого уже есть правило с ``Host(`…`)``, ничего дописывать не должен:
объявленное правило и есть согласие. Для собственных меток `hostbridge.enable` обязателен —
иначе список заполнился бы всем, что запущено на машине.

Имя принадлежит имени, а не контейнеру: если один и тот же хост объявляют два контейнера
(сервис и его редирект), запись остаётся одна и не исчезает при остановке одного из них.

## VPN с защитой от DNS-утечек

Клиенты вроде sing-box (v2rayN, режим TUN, `strict_route`) ставят фильтр WFP:

```
layer:     FWPM_LAYER_ALE_AUTH_CONNECT_V4
condition: FWPM_CONDITION_IP_REMOTE_PORT == 53      ← единственное условие
action:    FWP_ACTION_BLOCK
```

Условия на адрес в нём нет, поэтому под блокировку попадает и `127.0.0.1`: сокет
привязывается, `netstat` его показывает, правило NRPT на месте — а запрос до резолвера не
доходит, и браузер говорит «не удалось найти IP-адрес». Ни одного видимого признака поломки.

Выше этого блока лежат два разрешения того же фильтра: по идентификатору приложения самого
VPN и **по индексу его интерфейса**. Второе и есть выход: локальный адрес туннеля
принадлежит этой машине, сокет на нём принимает пакеты обычным образом, а обращение к нему
фильтр разрешает своим же правилом.

HostBridge проверяет это при запуске: пробует достучаться до `127.0.0.1:53` и, если получает
отказ по правам (`WSAEACCES`), дополнительно слушает адрес, через который уходит исходящий
трафик, и добавляет его в правило NRPT вторым сервером. Loopback остаётся первым, поэтому
пара работает и с поднятым туннелем, и без него. Обходов и трюков здесь нет — используется
разрешение, которое VPN написал сам.

Выключается настройкой `bypass_dns_filter: false`. Стоит выключить, если машина стоит в
сети, которой нельзя показывать резолвер: адрес выбирается по маршруту по умолчанию, и на
машине без VPN, но с каким-то другим фильтром порта 53, это может оказаться адрес в
локальной сети.

## Что происходит при закрытии

Демон, запущенный из окна, получает его PID и следит за ним. Закрыли приложение — демон
это замечает и завершается штатным путём: снимает свои правила NRPT (или маршрутизирующие
домены resolved), сбрасывает кэш DNS и убирает `netstate.json`. Так же он поступает, если
окно не закрыли, а убили: следить за процессом надёжнее, чем полагаться на пункт меню.

Демон, установленный службой, PID владельца не получает — он принадлежит машине, переживает
закрытие окна и поднимается после перезагрузки. Если демон всё-таки убили жёстко, оставшиеся
правила снимает `hostbridge-cli --repair`.

## Сборка из исходников

Нужен Python 3.10+.

```sh
bash build/build.sh          # Linux, macOS, Git Bash на Windows
pwsh build/build.ps1         # PowerShell
```

Результат — `dist/hostbridge-<os>-<arch>.tar.gz` на Linux и `.zip` на Windows.
Начиная с этапа M4 сборка под Windows даёт вместо архива инсталлятор
`hostbridge-setup-windows-x64.exe`, который сразу регистрирует службу.
`SKIP_TESTS=true` пропускает прогон тестов.

## Разработка

```sh
pip install -e ".[dev]"
pytest -m "not docker and not admin" -q
ruff check .
```

Маркеры тестов: `docker` — нужен работающий демон Docker, `admin` — нужны права
администратора или root, `network` — тест открывает локальные сокеты.

Автотесты не запускают внешние процессы: `system.run` — единственный шов, через который
приложение вызывает `netsh`, `resolvectl` и подобное, и фикстура в `tests/conftest.py`
превращает такой вызов в падение теста. Иначе случайный `netsh`, сбежавший из юнит-теста,
переконфигурировал бы DNS тому, кто запустил `pytest`.
